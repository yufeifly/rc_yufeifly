## 0. 一句话本质

**先可靠记录“需要通知”这件事，再异步投递；已经确认受理的任务不能因进程重启或外部故障而静默丢失。**

系统类似带存根的快递中转站：

- 业务系统交件，任务入库成功后才返回受理；
- 投递员可以失败后重试，但不能把未完成任务直接删除；
- 外部明确返回成功后，任务才进入成功终态；
- 长期失败的任务进入死信区，保留原因并允许人工重新投递。

本系统提供**至少一次投递（At-least-once）**。它优先保证“不丢”，并承认在超时或崩溃等不确定场景下可能重复。

## 2. 背景与问题

企业内部多个业务系统会在关键事件发生时调用外部供应商的 HTTP(S) API，例如：

- 用户通过广告渠道注册后通知广告平台；
- 用户订阅付款成功后通知 CRM；
- 用户购买商品后通知库存系统。

如果每个业务系统直接同步调用供应商，会产生以下问题：

1. **供应商耦合**：URL、鉴权 Header 和 Body 格式散落在各业务系统。
2. **故障扩散**：外部超时或不可用会占用业务请求，影响核心链路。
3. **可靠性不一致**：各业务系统自行实现重试，容易漏掉崩溃恢复、退避和死信。
4. **状态不可追踪**：难以回答任务是否发出、为何失败、何时重试。
5. **超时结果不确定**：调用超时不等于供应商未处理，盲目重试可能造成重复副作用。

因此，需要一个统一的内部通知服务，集中承接任务受理、供应商适配、异步投递、失败恢复和状态查询。

## 3. 产品目标

### 3.1 MVP 目标

| 编号 | 目标 | 可验证结果 |
|---|---|---|
| G1 | 解耦核心业务与外部 API | 调用方收到受理结果时不需要等待供应商响应 |
| G2 | 防止已受理任务因本服务重启而丢失 | 返回 `202` 后强杀并重启服务，任务仍可继续投递 |
| G3 | 统一供应商差异 | 至少演示两种不同 Header 或 Body 规则 |
| G4 | 自动处理临时故障 | 网络异常、超时、限流和 5xx 可有限重试 |
| G5 | 管理长期故障 | 重试耗尽或永久失败后进入死信，并可人工重新投递 |
| G6 | 支持问题排查 | 可查询状态、尝试次数、最近错误和下次重试时间 |
| G7 | 明确可靠性边界 | 文档、代码和测试均体现至少一次语义 |

### 3.2 MVP 成功信号

以下指标用于本地验收，不代表生产容量承诺：

- 已返回 `202 Accepted` 的任务，在重启恢复测试中丢失数为 0；
- 模拟供应商前两次返回 5xx、第三次返回 2xx 时，任务最终成功；
- 相同调用方使用相同幂等键和相同内容重复提交时，只产生一个逻辑任务；
- 单实例开发环境可稳定接收至少 50 请求/秒；
- 持久化存储健康时，接入接口本地 P95 响应时间不高于 200 ms；
- 每次真实投递都可关联到通知 ID 和尝试序号；
- 日志与查询响应不泄露供应商凭证。

### 3.3 非目标

MVP 不承诺：

- 严格恰好一次；
- 跨任务或同一业务对象的严格顺序；
- 多实例高可用和跨地域容灾；
- 动态供应商管理后台；
- 任意脚本或表达式模板引擎；
- 多租户计费和复杂权限体系；
- 无限重试；
- 任意 URL 代理；
- 供应商返回成功后的内部业务处理一定成功。

## 4. 用户与角色

### 4.1 业务接入方

内部业务系统的研发人员。

核心诉求：

- 快速提交，不被外部 API 延迟拖慢；
- 提交超时后可使用同一幂等键安全重试；
- 不需要了解供应商鉴权与报文细节；
- 必要时可以查询通知状态。

### 4.2 平台维护者

负责配置、部署、排障和故障恢复的研发或运维人员。

核心诉求：

- 能配置不同供应商；
- 能看到积压、失败和重试状态；
- 能在外部恢复或配置修复后重新投递；
- 能安全停机并验证重启恢复。

### 4.3 外部供应商

最终接收 HTTP(S) 通知的系统，不受本系统控制。

系统仅假设供应商：

- 提供可访问的 HTTP(S) 接口；
- 可约定请求格式和成功状态码；
- 最好支持使用稳定通知 ID 做幂等处理。

## 5. 核心概念

| 概念 | 定义 |
|---|---|
| 通知请求 | 调用方向通知服务表达的一次投递意图 |
| 通知任务 | 请求完成持久化后形成的内部可追踪实体 |
| 供应商 | 一组受信的 URL、鉴权、Header、Body 和成功判定规则 |
| 投递尝试 | 对供应商发起的一次真实 HTTP 请求 |
| 幂等键 | 调用方提供的稳定业务标识，用于识别重复提交 |
| 至少一次 | 已受理任务不会被主动丢弃，但供应商可能收到重复请求 |
| 不确定结果 | 请求可能已到达供应商，但本系统未获得明确结果 |
| 死信 | 不再自动重试、等待人工处理的任务 |
| Replay | 保留原通知 ID，将死信任务重新放回可投递状态 |

## 6. 系统边界

### 6.1 系统负责

1. 校验调用方提交的通知请求；
2. 对重复提交做逻辑去重和内容冲突检测；
3. 在返回成功受理前持久化任务；
4. 根据供应商配置构造 URL、Header 和 JSON Body；
5. 异步调用供应商 HTTP(S) API；
6. 按响应和错误类型决定成功、重试或死信；
7. 在服务重启后恢复未完成任务；
8. 保存任务状态、尝试次数和最近失败原因；
9. 提供单任务查询和死信 Replay；
10. 提供基础日志和健康检查，并为指标扩展预留边界。

### 6.2 系统不负责

1. 不产生注册、支付、库存等业务事件；
2. 不校验上游业务事实是否正确；
3. 不允许调用方提交任意目标 URL；
4. 不为供应商实现其内部业务幂等；
5. 不保证多个通知之间的业务顺序；
6. 不对供应商返回成功后的异步处理结果负责；
7. 不在 MVP 中提供管理后台、复杂工作流或通用集成平台能力。

### 6.3 可靠性终点

本系统能确认的成功仅为：

> 已按约定向供应商发出请求，并收到满足成功规则的 HTTP 响应。

如果供应商返回 2xx 后内部处理失败，本系统默认无法感知。未来只有在供应商提供回执或查询协议时才能扩展该边界。

## 7. 核心产品决策

### 7.1 异步受理

调用方提交后，系统完成校验、幂等判断和持久化，再返回 `202 Accepted`。

`202` 表示任务已可靠受理，不表示供应商已收到或已处理。

### 7.2 至少一次投递

系统选择至少一次，不宣称恰好一次。

原因是外部 HTTP 调用和本地状态更新无法组成同一个原子事务：

- 先记成功再发请求，可能产生假成功；
- 先发请求再记成功，可能在写回前崩溃，恢复后只能重试；
- 普通供应商 API 通常不支持两阶段提交。

因此，系统使用稳定通知 ID 帮助供应商去重，但不能单方面消除所有重复。

### 7.3 有限重试与人工恢复

- 临时故障使用指数退避和随机抖动；
- `Retry-After` 合法时优先参考，但受最大等待时间限制；
- 自动重试有明确上限；
- 永久失败或重试耗尽后进入死信；
- 外部恢复或配置修复后，由管理员触发 Replay。

### 7.4 供应商配置受控

调用方只提交 `provider` 标识。目标 URL、鉴权和转换规则由服务端可信配置决定，以避免 SSRF、凭证扩散和供应商配置重复。

### 7.5 MVP 不强制引入消息队列

首版优先采用“持久化任务存储 + 内置调度器 + 有界 Worker”完成闭环。

原因：

- 任务入库与排队可以落在同一事务边界；
- 本地运行和评审成本低；
- 可以完整验证幂等、重试、死信和崩溃恢复；
- 避免过早引入数据库与 MQ 双写一致性。

当单库存储、轮询或单实例成为真实瓶颈后，再演进为 Outbox + MQ + 独立 Worker。

## 8. 核心业务流程

### 8.1 正常流程

1. 调用方提交通知请求；
2. 系统鉴权、校验参数并识别供应商；
3. 系统依据“调用方 + 幂等键”创建或查找任务；
4. 事务提交后返回 `202 + notification_id`；
5. 调度器领取到期任务；
6. Worker 构造供应商请求并调用外部 API；
7. 收到符合规则的成功响应后，任务进入 `SUCCEEDED`。

### 8.2 临时失败

1. Worker 收到网络错误、超时、429 或 5xx；
2. 系统记录本次尝试和失败分类；
3. 系统计算下一次重试时间，任务进入 `RETRY_WAIT`；
4. 到期后重新领取；
5. 达到最大尝试次数后进入 `DEAD`。

### 8.3 崩溃恢复

1. Worker 领取任务时获得有期限的处理租约；
2. 正常完成时写回成功或失败结果；
3. 若进程在投递期间崩溃，租约最终过期；
4. 调度器恢复该任务并允许重新投递；
5. 旧 Worker 的迟到结果不得覆盖新一轮状态；
6. 由于外部请求可能已执行，重投时继续使用相同通知 ID。

### 8.4 长期故障恢复

1. 任务因永久失败或重试耗尽进入 `DEAD`；
2. 系统保留原始任务和失败上下文；
3. 管理员修复配置或确认供应商恢复；
4. 管理员填写原因并触发 Replay；
5. 任务保留原通知 ID 和历史记录，进入新一轮投递。

## 9. 功能需求

优先级定义：

- **P0**：MVP 必须完成，否则可靠投递闭环不成立；
- **P1**：建议完成，用于增强可运维性和评审体验；
- **P2**：明确后置，避免首版过度设计。

### 9.1 通知接入

#### FR-001 创建通知（P0）

提供内部 HTTP API 接收通知请求，至少包含：

- `idempotency_key`；
- `provider`；
- `event_type`；
- `payload`；
- 可选 `occurred_at`。

系统生成全局唯一的 `notification_id` 和服务端时间。

#### FR-002 请求校验（P0）

系统必须校验：

- 必填字段、长度和字符范围；
- `payload` 是 JSON 对象；
- 请求体不超过配置上限；
- `provider` 已配置且启用；
- `occurred_at` 符合 RFC3339；
- 不允许调用方覆盖系统保留 Header。

校验失败时不得创建任务。

#### FR-003 持久化后确认（P0）

只有任务事务提交成功后才能返回 `202`。存储不可用或提交失败时返回失败，不得先确认再异步补写。

#### FR-004 幂等提交（P0）

幂等范围为“调用方身份 + 幂等键”：

- 首次提交：创建任务；
- 相同键、相同有效内容：返回原任务，并标记为重复提交；
- 相同键、不同有效内容：返回 `409 Conflict`；
- 服务端通过规范化后的有效请求内容判断是否冲突。

#### FR-005 异步响应（P0）

接入链路不调用供应商。响应至少包含：

- `notification_id`；
- 当前状态；
- `duplicate`；
- 状态查询地址。

### 9.2 供应商适配

#### FR-101 供应商配置（P0）

每个供应商至少支持：

- 唯一标识和启用状态；
- HTTP 方法和受信目标 URL；
- 固定 Header；
- 凭证引用；
- 连接超时和请求总超时；
- Body 模式；
- 成功状态码规则；
- 最大自动尝试次数。

MVP 使用静态配置，修改后允许重启生效。

#### FR-102 Header 与鉴权（P0）

至少支持：

- 固定 Header；
- Bearer Token；
- API Key Header；
- 系统生成的通知 ID 和尝试序号 Header。

凭证从环境变量或等价的外部密钥来源注入，不进入任务数据和普通日志。

#### FR-103 Body 适配（P0）

MVP 至少支持两种模式：

1. `passthrough`：将业务 `payload` 作为请求 Body；
2. `envelope`：包装通知 ID、事件类型、发生时间和业务 Payload。

不实现通用脚本或表达式模板引擎。

#### FR-104 目标地址安全（P0）

- URL 仅来自服务端配置；
- 生产环境默认只允许 HTTPS；
- 默认不自动跟随重定向；
- 默认禁止访问环回、链路本地、私网和云元数据地址；
- 本地演示必须通过显式开发配置放开 HTTP 和环回地址。

### 9.3 调度与投递

#### FR-201 持久化调度（P0）

系统持续发现：

- 新创建的待投递任务；
- 已到重试时间的任务；
- 处理租约已过期的任务。

调度使用有界批次，不把全部积压加载到内存。

#### FR-202 原子领取与租约（P0）

系统通过原子更新、数据库锁或等价机制领取任务，并为领取结果生成租约。

正常情况下同一任务只由一个 Worker 执行；租约过期后可被重新领取。旧 Worker 的迟到写回必须被拒绝。

#### FR-203 有界 Worker（P0）

全局和单个供应商的投递并发数均可配置且有上限，不为每个积压任务无限创建协程，也不允许故障供应商占满全部 Worker。

#### FR-204 HTTP 资源边界（P0）

每次外部调用必须限制：

- 连接超时；
- 请求总超时；
- 最大响应读取大小；
- 最大并发数。

#### FR-205 投递结果记录（P0）

每次真实 HTTP 调用至少记录：

- 尝试序号；
- 开始和结束时间；
- HTTP 状态码；
- 错误类别和安全摘要；
- 是否可重试；
- 下一次重试时间；
- 投递耗时。

不得持久化明文凭证或完整外部响应体。

### 9.4 失败处理

#### FR-301 错误分类（P0）

默认规则：

| 结果 | 处理 |
|---|---|
| 配置的成功状态码，默认 2xx | 成功 |
| DNS、连接失败 | 重试 |
| 连接或读取超时 | 结果未知，重试 |
| 408、425、429 | 重试 |
| 500-599 | 重试 |
| 401、403 | 死信，等待凭证修复 |
| 其他 400-499 | 默认死信 |
| 重定向 | 默认不跟随，按失败处理 |
| 请求组装失败 | 死信 |
| 未知内部错误 | 记录并有限重试 |

供应商可覆盖成功状态码，但不能关闭超时和资源上限。

#### FR-302 退避策略（P0）

可重试失败使用指数退避并加入抖动。建议默认值：

- 初始间隔：5 秒；
- 退避倍数：2；
- 最大间隔：6 小时；
- 最大自动尝试：12 次；
- 抖动：基准间隔的 ±20%。

数值必须可配置；测试环境允许使用更短间隔。

#### FR-303 死信（P0）

满足以下任一条件时进入 `DEAD`：

- 自动尝试次数耗尽；
- 明确不可重试的响应；
- 无法构造合法请求；
- 供应商配置已失效；
- 检测到不可自动恢复的数据错误。

死信任务不再被普通调度器自动领取。

#### FR-304 Replay（P0）

系统提供内部管理 API 或 CLI 重新投递 `DEAD` 任务：

- 仅管理员可操作；
- 必须填写操作原因；
- 保留原 `notification_id`；
- 保留历史尝试记录；
- 使用新的投递轮次重新计数。

### 9.5 查询与运维

#### FR-401 查询通知（P0）

支持按 `notification_id` 查询，至少返回：

- 供应商和事件类型；
- 当前状态；
- 当前轮次及累计尝试次数；
- 创建、更新和最近尝试时间；
- 下一次重试时间；
- 最近错误分类、安全摘要和状态码。

普通调用方只能查询自身任务，管理员可查询全部任务。

#### FR-402 健康检查（P0）

提供：

- 存活检查：进程是否运行；
- 就绪检查：服务是否可受理请求，持久化存储是否可用。

单个供应商不可用不应直接让本服务判定为“不存活”。

#### FR-403 结构化日志（P0）

日志至少包含：

- 请求 ID；
- 通知 ID；
- 调用方；
- 供应商；
- 事件类型；
- 尝试序号；
- 状态变化；
- 错误分类。

日志不得包含认证密钥、Cookie、完整敏感 Payload 或完整外部响应体。

#### FR-404 基础身份与授权（P0）

MVP 至少支持基于静态 Token 的内部身份识别：

- 每个 Token 映射到稳定的调用方 ID 和角色；
- `producer` 可创建并查询自身任务；
- `admin` 可查询全部任务并执行 Replay；
- 非本机部署不得关闭认证；
- Token 使用常量时间比较，且不得出现在日志和响应中。

生产环境接入统一身份系统不属于 MVP。

#### FR-405 基础指标（P0）

必须暴露：

- 接入请求及结果计数；
- 各状态任务数；
- 当前积压量和最老到期任务年龄；
- 按供应商和错误分类统计的投递总数、成功数、失败数和重试数；
- 按供应商统计的投递耗时；
- Worker 使用量；
- 死信数量。

接口失败率不维护易失真的独立 Gauge，而是通过时间窗口内的失败计数除以总请求计数得到。告警必须同时设置最小请求量，避免低流量下单次失败触发噪声告警。

#### FR-406 基础限流（P1）

系统建议提供可配置的令牌桶限流：

- 接入侧按全局或调用方限制请求速率，超限返回 `429` 和 `Retry-After`；
- 投递侧按供应商限制请求速率，避免超过供应商配额；
- 令牌桶至少支持每秒速率和突发容量；
- 投递侧因本地限流而延后时，不消耗业务投递尝试次数。

#### FR-407 优雅停机（P1）

收到停机信号后停止领取新任务，在宽限期内等待在途任务；超时后退出，剩余任务依赖租约恢复。

## 10. API 产品契约

### 10.1 创建通知

`POST /v1/notifications`

请求示例：

```json
{
  "idempotency_key": "order_20260927_10001_paid",
  "provider": "crm",
  "event_type": "order.paid",
  "occurred_at": "2026-09-27T10:30:00+08:00",
  "payload": {
    "order_id": "20260927_10001",
    "customer_id": "u_12345",
    "amount": 19900,
    "currency": "CNY"
  }
}
```

受理响应示例：

```json
{
  "notification_id": "ntf_01K...",
  "status": "PENDING",
  "duplicate": false,
  "status_url": "/v1/notifications/ntf_01K..."
}
```

主要状态码：

| 状态码 | 含义 |
|---|---|
| 202 | 已持久化受理，或相同内容的重复请求映射到原任务 |
| 400 | 请求格式或字段错误 |
| 401/403 | 未认证或无权提交 |
| 404 | 供应商不存在或未启用 |
| 409 | 幂等键对应不同内容 |
| 413 | 请求体过大 |
| 429 | 接入被限流 |
| 503 | 持久化失败或服务暂不可受理 |

### 10.2 查询通知

`GET /v1/notifications/{notification_id}`

响应示例：

```json
{
  "notification_id": "ntf_01K...",
  "provider": "crm",
  "event_type": "order.paid",
  "status": "RETRY_WAIT",
  "delivery_round": 1,
  "attempt_count": 3,
  "next_attempt_at": "2026-09-27T10:35:00+08:00",
  "last_error": {
    "category": "UPSTREAM_5XX",
    "http_status": 503,
    "message": "upstream service unavailable"
  }
}
```

### 10.3 重新投递

`POST /v1/notifications/{notification_id}/replay`

请求示例：

```json
{
  "reason": "CRM credential rotated and verified"
}
```

默认仅允许管理员对 `DEAD` 任务操作。

## 11. 状态模型

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `PENDING` | 已受理，等待首次投递 | 否 |
| `DELIVERING` | 已被 Worker 领取，租约有效 | 否 |
| `RETRY_WAIT` | 本次失败，等待下次重试 | 否 |
| `SUCCEEDED` | 收到符合规则的成功响应 | 是 |
| `DEAD` | 自动恢复结束，等待人工处理 | 是，可 Replay |

允许的核心状态转换：

```text
PENDING -> DELIVERING
RETRY_WAIT -> DELIVERING
DELIVERING -> SUCCEEDED
DELIVERING -> RETRY_WAIT
DELIVERING -> DEAD
DELIVERING -> PENDING      # 租约过期恢复
DEAD -> PENDING            # 人工 Replay
```

状态不变量：

1. 返回 `202` 的任务必须已存在于持久化存储；
2. `SUCCEEDED` 和 `DEAD` 不被普通调度器领取；
3. `DELIVERING` 必须存在有效租约；
4. 状态、计数和下次执行时间需要原子更新；
5. 过期租约只允许当前新持有者写回结果；
6. 超时和崩溃后的外部结果标记为未知，不能假定未送达。

## 13. 非功能需求

### 13.1 可靠性

- 持久化成功晚于受理确认；
- 持久化存储是任务事实源，内存队列只能用于唤醒或加速；
- 服务重启后自动恢复未完成任务；
- 任务领取和结果写回具备并发保护；
- 重试有分类、退避、抖动和上限；
- 死信可查询、可 Replay；
- 所有投递携带稳定通知 ID。

### 13.2 性能与资源

- 接入链路不执行供应商 HTTP；
- 调度可按状态和下次执行时间高效查询；
- 扫描批次、Worker 数量、请求体和响应体均有上限；
- 积压时不将全部任务加载到内存；
- MVP 以单实例 50 请求/秒为验证基线。

### 13.3 安全

- 服务面向内部网络；
- 生产环境必须启用身份认证；
- 管理操作需要独立权限并记录审计；
- 目标地址来自可信配置并执行网络访问限制；
- 凭证通过外部注入，不写入任务、响应和普通日志；
- 错误响应不暴露内部堆栈和存储细节。

### 13.4 可观测性

对任一任务，维护者应能回答：

1. 谁在何时提交；
2. 是否命中幂等；
3. 当前状态是什么；
4. 已尝试多少次；
5. 最近为什么失败；
6. 何时再次尝试；
7. 是否进入死信；
8. 是否发生过人工 Replay。

### 13.5 可维护性

- 供应商差异集中在明确的适配边界；
- 状态机、重试策略、调度和 HTTP 执行可独立测试；
- 配置在启动时严格校验，错误配置快速失败；
- 核心状态转换不散落在无约束调用点。

## 14. 异常与边界场景

| 场景 | 预期行为 |
|---|---|
| 参数不合法 | 返回 400，不创建任务 |
| 供应商不存在 | 返回 404，不创建任务 |
| 同键同内容重复提交 | 返回原任务，不重复创建 |
| 同键不同内容提交 | 返回 409 |
| 数据库提交失败 | 返回 503，不返回 202 |
| 入库后、响应前连接断开 | 调用方使用同一幂等键重试 |
| 返回 202 后服务崩溃 | 重启后继续投递 |
| 供应商返回成功状态码 | 标记 `SUCCEEDED` |
| 供应商返回 429 或 5xx | 退避重试 |
| 供应商持续失败 | 达到上限后进入 `DEAD` |
| 供应商返回普通 4xx | 默认进入 `DEAD` |
| 请求发出后响应超时 | 视为未知，使用相同通知 ID 重试 |
| 外部成功但本地写回前崩溃 | 恢复后可能重复投递 |
| 两个 Worker 同时发现任务 | 只有成功领取者持有有效租约 |
| 旧 Worker 延迟写回 | 写回失败，不覆盖新状态 |
| 外部返回巨大响应 | 仅读取有限前缀，不保存完整响应 |
| 供应商返回重定向 | 默认不跟随 |
| 凭证过期 | 401/403 进入死信，等待修复 |

## 15. 验收标准

### AC-001 可靠受理

**Given** 持久化存储可用
**When** 调用方提交合法通知
**Then** 系统在任务持久化后返回 `202` 和唯一通知 ID。

### AC-002 不虚假确认

**Given** 持久化提交失败
**When** 调用方提交合法通知
**Then** 系统返回失败，不返回 `202`。

### AC-003 重启不丢任务

**Given** 调用方已经收到 `202`，任务尚未成功
**When** 服务被强制终止并使用同一存储重启
**Then** 任务最终可被重新发现和投递。

### AC-004 临时失败自动恢复

**Given** 供应商前两次返回 5xx，第三次返回成功
**When** 系统投递通知
**Then** 任务经过两次退避重试后进入 `SUCCEEDED`。

### AC-005 永久失败进入死信

**Given** 供应商返回不可重试的 4xx
**When** 系统完成本次投递
**Then** 任务进入 `DEAD`，并记录错误分类和状态码。

### AC-006 重试耗尽

**Given** 供应商持续返回 5xx
**When** 尝试次数达到配置上限
**Then** 任务进入 `DEAD`，不再自动调度。

### AC-007 人工恢复

**Given** 一个 `DEAD` 任务且供应商已恢复
**When** 管理员携带原因触发 Replay
**Then** 任务保留原通知 ID，进入新投递轮次并可最终成功。

### AC-008 幂等提交

**Given** 已存在某调用方和幂等键对应的任务
**When** 调用方使用相同有效内容再次提交
**Then** 系统返回原通知 ID，任务数量不增加。

### AC-009 幂等冲突

**Given** 幂等键已被使用
**When** 调用方使用相同键提交不同有效内容
**Then** 系统返回 `409 Conflict`。

### AC-010 崩溃中的不确定结果

**Given** Worker 已发出请求但尚未写回结果
**When** Worker 进程崩溃
**Then** 租约过期后任务可重新投递，并继续携带相同通知 ID。

### AC-011 供应商差异

**Given** 两个供应商具有不同 Header 或 Body 规则
**When** 分别投递同一内部事件
**Then** 两个 Mock 端均收到符合自身规则的请求。

### AC-012 敏感信息保护

**Given** 供应商配置包含 Token 或 API Key
**When** 投递成功或失败
**Then** 日志和查询响应均不出现明文凭证。

### AC-013 有界并发

**Given** 存在大量积压任务
**When** 调度器持续投递
**Then** 同时执行的外部请求不超过配置上限。

### AC-014 状态可追踪

**Given** 任务经历过失败和重试
**When** 查询该任务
**Then** 可看到当前状态、尝试次数、最近错误和下次重试时间。

### AC-015 身份与权限隔离

**Given** 系统启用认证，存在 producer 和 admin 两种身份
**When** producer 查询其他调用方任务或执行 Replay
**Then** 请求被拒绝；admin 可以执行相应管理操作。

### AC-016 失败率可观测

**Given** 某供应商同时存在成功和失败的投递
**When** 查询监控指标
**Then** 可按供应商和时间窗口计算总请求数、失败数和失败率，并按错误分类定位主要失败原因。

## 18. 关键取舍

### 18.1 不做恰好一次

单方 HTTP 调用无法原子提交“供应商副作用”和“本地成功状态”。系统选择不丢任务，并通过稳定通知 ID 把重复风险交给双方幂等协作。

### 18.2 不以内存队列作为事实源

内存队列可以降低调度延迟，但进程退出即丢失。它只能作为唤醒机制，持久化存储才是恢复依据。

### 18.3 不在首版引入 MQ

MQ 会同时引入发布确认、消费确认、数据库双写、消息积压和双重重试治理。当前规模下，这些复杂度不能提升核心可靠性证明。

### 18.4 不实现通用模板引擎

任意模板和脚本会引入安全、调试、版本管理和运行时隔离问题。两种明确 Body 模式足以验证供应商适配边界。

### 18.5 不保证顺序

并发、重试和崩溃恢复都会打乱顺序。若未来业务确实要求顺序，需要引入分区键、同分区串行和序号校验，不应在没有业务要求时提前承担复杂度。

### 18.6 不把流量治理放进 P0

复杂优先级、积压降级和熔断属于有价值的生产增强，但不是证明“可靠受理、失败重试、死信恢复”的必要条件。首版先保证正确性和可观测性闭环，基础令牌桶限流放在 P1，再按真实瓶颈演进。

## 20. 默认假设与待审查决策

原始作业没有规定以下内容。为形成可执行 PRD，当前草案采用这些默认值：

| 决策 | 当前默认值 | 审查重点 |
|---|---|---|

| 数据保留 | MVP 不自动删除 | 后续需补归档策略 |
| 管理方式 | HTTP API 或 CLI | 不做管理后台 |

这些默认值在 PRD 审查通过后，才能作为技术设计输入；技术设计可在不改变产品语义的前提下调整具体实现参数。

---

## 21. 交付物与 AI Coding 过程

最终 GitHub 仓库至少包含：

1. `docs/PRD.md`：需求边界、优先级和验收标准；
2. 技术设计文档：架构、数据模型、状态机和故障恢复；
3. MVP 代码与配置示例；
4. 自动化测试、Mock 供应商和演示脚本；
5. `README.md`：运行、验证、设计摘要和取舍；
6. `AI_USAGE.md`：
   - AI 在哪些阶段提供帮助；
   - AI 给出过哪些建议；
   - 哪些建议未采纳及原因；
   - 哪些关键决策由提交者做出；
   - 如何验证 AI 生成内容；
7. 可审查的 Git 提交历史，按 PRD、技术设计、实现、测试和文档等阶段保留过程。

本阶段只生成 PRD 草案，不执行 Git 提交。PRD 经人工审查后，再进入提交或下一阶段。

## 22. PRD 完成定义

满足以下条件后，PRD 可进入技术设计阶段：

- 目标、边界和非目标无冲突；
- 至少一次语义获得确认；
- 幂等范围和冲突规则获得确认；
- 成功、重试、死信和 Replay 规则获得确认；
- P0/P1/P2 范围获得确认；
- 默认假设不存在阻塞性分歧；
- 每项 P0 都有可执行验收方式；
- PRD 与原始作业要求一致；
- 用户明确审查通过。
